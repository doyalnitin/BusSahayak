4. PostgreSQL — Seat Matrix Caching & Storage
SEAT_CACHE TABLE
-- Cache ZuelPay seat data (refresh every 5 min) CREATE TABLE seat_cache ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), bus_id VARCHAR(50) NOT NULL, seat_id VARCHAR(10) NOT NULL, row_letter VARCHAR(5), position VARCHAR(20), -- window/middle/aisle side VARCHAR(10), -- left/right seat_type VARCHAR(20), -- seater/sleeper base_status VARCHAR(20), -- from ZuelPay price DECIMAL(10,2), features JSONB, last_synced TIMESTAMPTZ DEFAULT NOW(), UNIQUE(bus_id, seat_id) ); -- Index for fast lookups CREATE INDEX idx_seat_cache_bus ON seat_cache(bus_id); -- Booking records (permanent) CREATE TABLE bookings ( id UUID PRIMARY KEY, bus_id VARCHAR(50), seat_id VARCHAR(10), passenger_name VARCHAR(100), phone VARCHAR(15), status VARCHAR(20), -- locked/confirmed/expired created_at TIMESTAMPTZ DEFAULT NOW() );
CACHE REFRESH STRATEGY
Why cache ZuelPay data?
- ZuelPay API has rate limits (100 req/min)
- Seat layout changes slowly (every few minutes)
- Caching reduces API calls by 90%

# Background job: Sync seat cache every 5 minutes async def sync_seat_cache(bus_id: str): # 1. Fetch fresh data from ZuelPay zuelpay_data = await zuelpay.get_seats(bus_id) # 2. Upsert into PostgreSQL cache for seat in zuelpay_data["seats"]: await db.execute(""" INSERT INTO seat_cache (bus_id, seat_id, row_letter, position, side, seat_type, base_status, price) VALUES ($1,$2,$3,$4,$5,$6,$7,$8) ON CONFLICT (bus_id, seat_id) DO UPDATE SET base_status = EXCLUDED.base_status, last_synced = NOW() """, bus_id, seat["id"], seat["row"], seat["position"], seat["side"], seat["type"], seat["status"], seat["price"])
Refresh triggers:
Periodic: Every 5 minutes via cron job
On-demand: When user requests seats
Stale: If last_synced > 5 min, refresh first
SQL Query: Get Full Seat Matrix for a Bus
-- Get all seats with live status (cached ZuelPay + Redis locks + PostgreSQL bookings) SELECT sc.seat_id, sc.row_letter, sc.position, sc.side, sc.seat_type, sc.price, CASE WHEN b.status = 'confirmed' THEN 'booked' WHEN b.status = 'locked' THEN 'locked' WHEN sc.base_status = 'booked' THEN 'booked' ELSE 'available' END AS live_status FROM seat_cache sc LEFT JOIN bookings b ON sc.bus_id = b.bus_id AND sc.seat_id = b.seat_id AND b.status IN ('locked', 'confirmed') WHERE sc.bus_id = 'peela_001' ORDER BY sc.row_letter, sc.seat_id;

# FastAPI function that Gemini calls for seat matrix
@app.post
("/api/v1/get-seats")
async def
get_seat_matrix(request: SeatRequest):
  # STEP 1: Get cached seat data from PostgreSQL
  seats = await db.fetch(
    """SELECT * FROM seat_cache       WHERE bus_id = $1       ORDER BY row_letter, seat_id""",
    request.bus_id
  )

  # STEP 2: Check if cache is stale (>5 min old)
  if seats[0].last_synced < datetime.now() - timedelta(5):
    await sync_seat_cache(request.bus_id)
    seats = await db.fetch(...)

  # STEP 3: Get Redis locks
  locked_keys = await redis.keys(f"seat_lock:{request.bus_id}:*")
  locked_seats = [k.split(":")[2] for k in locked_keys]

  # STEP 4: Get confirmed bookings
  booked = await db.fetch(
    """SELECT seat_id FROM bookings       WHERE bus_id=$1 AND status='confirmed'""",
    request.bus_id
  )

  # STEP 5: Merge all data
  matrix = for seat in seats:
    if seat.id in booked:
      seat.live_status = "booked"
    elif seat.id in locked_seats:
      seat.live_status = "locked"
    else:
      seat.live_status = "available"

  # STEP 6: Build voice-ready response
  return {
    "bus_type": "seater",
    "layout": "2+2",
    "total": 40,
    "available_count": 11,
    "seats": [
      { "id": "A1", "pos": "window", "status": "available" },
      { "id": "A2", "pos": "middle", "status": "available" },
      ... # all 40 seats
    ]
  }

10. Judge Q&A — Seat Matrix Specific
Q1: How does AI know which seat is window/middle/aisle?
ZuelPay API returns position: "window" for each seat. PostgreSQL caches this. FastAPI includes it in the merged response. Gemini speaks "A1 Window seat, khali" — user knows the position without seeing.
Q2: What if user says "window seat do" instead of "A1"?
Gemini calls get_seats(bus_id, filter="window") → FastAPI filters seats where position="window" and status="available" → Returns A1, B2, C4 → Gemini speaks them → User picks one.
Q3: Why cache in PostgreSQL instead of reading ZuelPay every time?
ZuelPay has rate limits (100 req/min). With 1000 users, we'd hit limits instantly. Caching reduces API calls by 90%. Seat layout changes every few minutes, not every second. Cache refreshes every 5 min.
Q4: How does AI handle different bus types (seater vs sleeper)?
ZuelPay returns bus_type: "seater" or "sleeper". FastAPI includes this in response. Gemini adjusts readout: "Seater bus hai, 2+2 layout" vs "Sleeper bus hai, 2+1 layout". Different voice format for each.
Q5: What if Redis and PostgreSQL disagree on seat status?
PostgreSQL is source of truth. Redis is for real-time locks only. If conflict: PostgreSQL wins. Redis lock is temporary (60 min). If Redis says "locked" but PostgreSQL says "confirmed" → seat is booked. Priority: Booked > Locked > Available.
Q6: Can user select multiple seats in one go?
Yes! User says "A1 aur A2 dono lelo" → Gemini calls create_booking twice → FastAPI locks both seats atomically → Two Redis keys created → Both appear in PostgreSQL as locked.
