1. The Problem & Our Solution
THE PROBLEM
India has 40+ million blind/visually impaired people.

Current bus booking apps (RedBus, AbhiBus) are 100% visual:
- Need to see the screen to navigate
- Need to read bus names, times, prices
- Need to tap specific seats on a grid
- Need to type payment details

Result: Blind people CANNOT book bus tickets independently. They must ask friends, family, or travel agents every time.
OUR SOLUTION
BusSahayak: Voice-First Bus Booking

User holds the MIC button and speaks naturally in Hindi/Hinglish:

User: "Delhi se Jaipur kal ke liye AC bus dikhao"
BusSahayak: "5 AC buses milen. Peela Travels - 550 rupay, 2:30 PM. Bol dijiye konsi chahiye."

Result: Blind user books independently, speaks naturally, gets audio confirmation. No screen needed.

g) Audio streamed back to user

6. Three Operating Modes (Different User Needs)
MODE 1
VOICE ONLY
For: Completely blind users

How it works:
- Screen is completely locked (no touch)
- User holds MIC → speaks → hears response
- Touch events are blocked entirely
- Only voice input accepted

Example user: Ram, 45, completely blind since birth. Has never seen a screen. Navigates entirely by screen reader. Holds phone in left hand, presses MIC with right thumb.

LOCKED TOUCH VOICE ONLY
MODE 2
DYNAMIC SWITCH
For: Low vision / partially sighted

How it works:
- Starts locked (voice-only by default)
- User says "unlock" → touch enabled
- Can now tap buttons, scroll, see UI
- Says "lock" → back to voice-only

Example user: Sunita, 28, diabetic retinopathy. Can see large text and high-contrast UI. Starts with voice, unlocks to check bus times visually, locks again for booking.

VOICE FIRST UNLOCK BY VOICE
MODE 3
DUAL COMBINED
For: Tech-savvy VI users

How it works:
- Touch ALWAYS enabled
- Voice and touch work together
- Tap to select → voice to confirm
- Best of both worlds

Example user: Amit, 22, BCA student with low vision. Uses TalkBack + voice. Taps bus card to select, holds MIC to say "confirm karo". Fastest flow.

TOUCH ALWAYS ON VOICE + TOUCH
Mode Toggle (Voice Command)
User says: "Mode 1 pe set karo" → Screen locked, voice only
User says: "Mode 2 pe set karo" → Dynamic switch enabled
User says: "Mode 3 pe set karo" → Dual combined enabled
Screen reader button: Toggle modes via accessibility menu

10. Judge Q&A Preparation (25+ Questions)
Technical Questions
Q1: How is this different from just using Siri or Google Assistant?
Siri/Google are general-purpose. BusSahayak is specialized for bus booking — it knows bus routes, seat layouts, pricing, and the 60-minute tele-confirmation flow. Gemini is given function declarations (search_buses, get_seats, create_booking) so it can directly call bus APIs. Also, Siri can't do barge-in (interrupt mid-sentence), and doesn't understand Indian bus booking context.
Q2: What happens when internet is slow or unavailable?
We have a fallback pipeline: Vosk (offline STT, 50ms) + Gemma 2B Q4 (offline LLM, 150ms) + Piper (offline TTS, 50ms). Total offline latency: ~260ms. This handles low-connectivity areas in rural India. The offline engine supports basic search and booking. Full Gemini features require internet.
Q3: How do you ensure the voice recognition works with Indian accents?
Gemini's speech model is trained on diverse global data including Indian languages. We also use Hindi/Hinglish in our system prompt so Gemini expects mixed language input. For the offline fallback, Vosk has Hindi language models. We can fine-tune Custom Speech on Azure for even better accuracy with regional accents.
Q4: What about payment? Can blind users pay?
Our 60-minute tele-confirmation flow solves this. After voice booking, the manager dashboard shows the booking. Manager calls the blind user, confirms details, and processes payment (cash/UPI at pickup, or manager pays and user reimburses). We're also exploring UPI voice integration (NPCI's UPI Voice) for future.
Q5: How is Gemini function calling different from ChatGPT function calling?
Gemini's function calling is real-time and streaming — it can call functions mid-conversation without waiting for a complete response. ChatGPT's is request-response. Gemini also handles audio natively (multimodal), while ChatGPT's function calling is text-only. This means Gemini can hear you, call an API, and respond with audio — all in one WebSocket connection.
Impact & Market Questions
Q6: How many blind people actually use smartphones?
According to WHO and Indian government data, there are ~40 million blind people in India. A 2023 survey by National Association of the Blind found that ~30% of blind Indians own smartphones (Android). That's ~12 million potential users. Plus 200 million+ with low vision who can benefit from Mode 2/3.
Q7: What's the business model? How do you make money?
Commission per booking (₹5-15 per ticket via ZuelPay partner program). Manager dashboard SaaS (₹500/month per travel agent). Premium voice features (₹99/month for advanced AI). Government accessibility grants (ADIP scheme). The core booking feature is free for blind users.
Q8: Why not just use RedBus accessibility mode?
RedBus has no accessibility mode. Their app is 100% visual. Even apps with "accessibility" features just add screen reader labels — they don't provide voice-first interaction. BusSahayak is the first app where the ENTIRE flow is voice-operated. You never need to look at the screen.
Technical Architecture Questions
Q9: Why React Native and not Flutter?
React Native has better accessibility APIs out of the box (AccessibilityInfo, TalkBack integration). Expo SDK 52 makes deployment easier (EAS Build). Our team knows React/JS better. Flutter's accessibility has known issues with screen readers on Android. For a hackathon, faster iteration matters.
Q10: How does the 60-minute seat lock work technically?
When user says "book karo", FastAPI creates a Redis key with TTL 3600 seconds: seat_lock:{bus_id}:{seat_id}. The manager dashboard polls Redis every 30 seconds for pending locks. Manager calls blind user within 60 minutes. If confirmed → seat permanently reserved. If not → TTL expires, seat auto-releases back to pool. Zero manual intervention needed.
Q11: What about barge-in? Can user interrupt the bot?
Yes. Gemini Multimodal Live API supports native barge-in. If the user starts speaking while BusSahayak is responding, Gemini automatically stops the current response and processes the new input. This is critical for natural conversation — blind users shouldn't have to wait for the bot to finish speaking.
Q12: How do you handle multiple users booking the same seat?
Redis-based distributed locking with atomic SET NX operations. When User A locks seat B5, the Redis key is set with NX (only if not exists) + TTL. User B trying to book B5 gets "seat already locked" error. The lock is per-user and releases after 60 minutes if not confirmed. This handles concurrent access safely.
Presentation & Demo Questions
Q13: Is this a working prototype or just a concept?
Working prototype. Phase 1 is complete — 28 source files, 7 screens, 6 components, 5 hooks, Zustand store, mock data with 50+ buses across 40 cities. Voice AI engine is built with Gemini integration. We have a live demo ready. The mock data allows full booking flow without depending on live ZuelPay API.
Q14: What's the biggest risk for this project?
Two risks: (1) Gemini API costs at scale — $0.02/15s adds up. Mitigation: offline fallback for basic queries, caching frequent routes. (2) Manager adoption — the tele-confirmation flow depends on managers answering calls. Mitigation: auto-call system, FCM push, manager dashboard with one-tap confirm.
Q15: How does this fit SIH26002 (Smart Logistics & Accessibility for NER)?
North Eastern Region has the highest percentage of visually impaired population in India (Assam: 2.4%, national average: 1.8%). NER also has poor road connectivity — inter-state bus travel is critical. Our app enables blind users in Guwahati, Shillong, Imphal to book buses independently. The offline fallback works in low-connectivity NER areas. We're adding NER cities (Guwahati, Shillong, Imphal, Agartala) to our database.

13. Common Judge Traps & How to Handle Them
TRAP: "Isn't this just a wrapper around Gemini?"
Answer: No. Gemini is our voice engine, but the entire system is custom-built:

- Custom system prompt for Indian blind users
- Custom function declarations for bus booking
- Custom seat lock mechanism with Redis TTL
- Custom 3 operating modes for different VI needs
- Custom manager dashboard for tele-confirmation
- Custom offline fallback (Vosk + Gemma + Piper)
- Custom accessibility layer (TalkBack, VoiceOver)

We're using Gemini as infrastructure, not as the product.
TRAP: "What about data privacy?"
Answer: We take privacy seriously:

- Audio is processed in real-time, not stored
- No voice recordings saved on our servers
- User data encrypted at rest (AES-256)
- GDPR/DPDP Act compliant
- Audio streams directly to Gemini, not through our server
- Manager only sees booking details, not voice recordings
- Redis seat locks are ephemeral (auto-expire)

Voice is processed, not stored.
TRAP: "How will you scale to millions?"
Answer: Architecture is designed for scale:

- FastAPI async handles 10K+ concurrent connections
- Redis cluster for seat locks (distributed)
- PostgreSQL with read replicas
- Gemini API auto-scales (Google manages)
- CDN for static assets (Expo updates)
- Horizontal scaling via Kubernetes

For hackathon: single server. For production: auto-scaling.
TRAP: "What's your unfair advantage?"
Answer: Three things competitors can't easily replicate:

1. First-mover: No voice-first bus booking app exists in India
2. 60-min tele-confirmation: Unique trust mechanism for blind users
3. 3 operating modes: Adapts to completely blind, low vision, and tech-savvy VI

Plus: We're the only team combining Gemini Live API with accessibility for Indian bus travel.
